# User Story: Document Navigator for AI-Generated Markdown Files

## Feature Summary

Implement a **Document Navigator** for a markdown reading application aimed at casual users who open AI-generated `.md` files.

The feature combines three navigation aids:

1. A **right-edge document mini-map** for long markdown files.
2. **Collapsible sections** based on markdown headings.
3. A **floating minimalist table of contents** for quick section jumping.

The goal is to make long AI-generated markdown documents feel readable, browsable, and less overwhelming without forcing users into a developer-style editor interface.

---

## Product Context

### Current app state

The app currently supports:

- Opening markdown files.
- Showing raw markdown text on one side.
- Showing rendered markdown preview on the other side.

### Target user

A casual user who receives or downloads a `.md` file generated by an AI tool and wants to read it comfortably.

They may not understand markdown syntax and should not need to.

### Design principle

Default to **reading comfort**.

Raw markdown and advanced controls should be available, but the user should first experience the file as a clean readable document.

---

## Primary User Story

### Story 1: Navigate long markdown documents easily

As a casual user,  
I want an easy way to navigate a long AI-generated markdown document,  
so that I can jump between sections without scrolling endlessly or reading the raw markdown.

### Acceptance Criteria

- The app detects headings from the markdown document.
- The app generates a navigable document structure from those headings.
- The user can jump to any heading from a floating table of contents.
- The user can collapse and expand sections by heading.
- The user can use a right-edge mini-map to understand document length and structure.
- The current visible section is highlighted in the navigator.
- The feature works in rendered reading mode.
- The feature does not require the user to edit raw markdown.

# Feature 1: Floating Minimalist Table of Contents

## User Story

As a casual reader,  
I want a small floating “Contents” control,  
so that I can quickly see the document sections only when I need them.

## Functional Requirements

### FR-1.1: Show floating Contents button

Display a small floating button labeled:

```text
Contents
```

The button should appear in reading mode when the markdown file has at least two headings.

### FR-1.2: Open compact table of contents

When the user clicks the button, show a compact overlay containing the document headings.

The overlay should:

- Show heading text.
- Preserve heading hierarchy visually.
- Highlight the current section.
- Allow the user to click a heading to jump to that section.
- Close automatically after selecting a heading.
- Close when the user clicks outside the overlay.
- Close when the user presses `Esc`.

### FR-1.3: Support keyboard access

The Contents button must be reachable by keyboard.

Suggested shortcut:

```text
Ctrl + K
```

When triggered, focus should move into the table of contents overlay.

### FR-1.4: Keep the overlay lightweight

Do not use a large sidebar or heavy navigation panel for this feature.

The floating table of contents should feel like a temporary reading aid, not a permanent workspace.

## Acceptance Criteria

- Given a document with headings, when I click `Contents`, I see a compact heading list.
- Given the TOC is open, when I click a heading, the document scrolls to that section.
- Given the TOC is open, when I press `Esc`, the TOC closes.
- Given I use keyboard navigation, I can open, navigate, and close the TOC without a mouse.
- Given I scroll through the document, the current section highlight updates.

# Feature 2: Collapsible Sections per Heading

## User Story

As a casual reader,  
I want to collapse sections of a markdown document,  
so that I can reduce clutter and focus only on the parts I care about.

## Functional Requirements

### FR-2.1: Add collapse controls to headings

Each rendered heading should have a collapse or expand control.

Example visual behavior:

```text
▾ Overview
▸ Requirements
▾ Implementation Notes
```

### FR-2.2: Collapse section content

When a heading is collapsed:

- Hide the content under that heading.
- Continue hiding content until the next heading of the same or higher level.
- Preserve nested heading relationships.

Example:

```md
## Section A
Text A

### Subsection A1
Text A1

## Section B
Text B
```

If `Section A` is collapsed, hide:

- `Text A`
- `Subsection A1`
- `Text A1`

But do not hide `Section B`.

### FR-2.3: Preserve section heading visibility

Collapsed headings must remain visible.

Only the content under the heading should be hidden.

### FR-2.4: Add global collapse controls

Add simple global controls:

- Collapse all
- Expand all

Optional but recommended:

- Collapse all below current heading level
- Show headings only

### FR-2.5: Remember collapse state

The app should remember collapsed and expanded state per opened file during the current session.

Optional future enhancement:

- Persist collapse state across app restarts using local storage or app settings.

## Acceptance Criteria

- Given a section is expanded, when I click its collapse control, its content is hidden.
- Given a section is collapsed, when I click its expand control, its content is shown again.
- Given a section has nested subsections, collapsing the parent hides the nested content.
- Given I collapse a section, the heading remains visible.
- Given I click `Expand all`, all hidden sections become visible.
- Given I click `Collapse all`, only headings remain visible.

# Feature 3: Right-Edge Document Mini-Map

## User Story

As a reader of long AI-generated markdown files,  
I want a small visual map of the document on the side,  
so that I can understand the structure and jump around quickly.

## Functional Requirements

### FR-3.1: Show mini-map for long documents only

Display the mini-map only when the document is long enough to benefit from it.

Suggested condition:

- Render mini-map when document has at least 5 headings, or
- Render mini-map when document height is at least 2.5 times the viewport height.

### FR-3.2: Display document structure

The mini-map should appear as a thin vertical strip on the right edge of the reading area.

It should represent:

- Headings
- Current viewport position
- Long text-heavy sections
- Code blocks
- Tables
- Task lists

The mini-map does not need to show readable text. It should be a structural overview.

### FR-3.3: Support interaction

The user can:

- Click a region of the mini-map to jump to that approximate document location.
- Drag the viewport indicator to scroll.
- Hover a heading marker to see the section title.

### FR-3.4: Highlight current viewport

The mini-map must show which part of the document is currently visible.

### FR-3.5: Avoid visual clutter

The mini-map should be subtle by default.

Suggested behavior:

- Low visual emphasis when idle.
- Slightly stronger contrast on hover.
- Do not block document text.
- Hide or compact on small screens.

## Acceptance Criteria

- Given a long document, the mini-map appears on the right edge.
- Given a short document, the mini-map stays hidden.
- Given I scroll, the mini-map viewport indicator moves correctly.
- Given I click a mini-map region, the document scrolls to that location.
- Given I hover a heading marker, I see the heading title.
- Given I am on a small mobile screen, the mini-map does not obstruct reading.

# Shared Technical Requirements

## Markdown parsing

The implementation must extract a document outline from parsed markdown.

Each heading should produce an outline item with:

```ts
type MarkdownHeading = {
  id: string;
  level: number;
  text: string;
  startOffset?: number;
  endOffset?: number;
  element?: HTMLElement;
};
```

If the app already uses a markdown parser, extend the existing pipeline instead of adding a second parser.

## Heading IDs

Each rendered heading must receive a stable ID.

Rules:

- Generate slug from heading text.
- Ensure uniqueness if headings repeat.
- Keep IDs stable across re-renders when possible.

Example:

```md
## Project Overview
## Project Overview
```

Generated IDs:

```text
project-overview
project-overview-2
```

## Section boundary detection

A section begins at a heading and ends before the next heading of the same or higher level.

Example:

```md
# A
## B
### C
## D
```

Section `B` includes `C` but ends before `D`.

## Scroll tracking

Implement current-section detection using `IntersectionObserver` when available.

Fallback to scroll position calculation if needed.

## Responsive behavior

Desktop:

- Floating TOC available.
- Collapsible sections available.
- Mini-map visible for long documents.

Tablet:

- Floating TOC available.
- Collapsible sections available.
- Mini-map optional or compact.

Mobile:

- Floating TOC available.
- Collapsible sections available.
- Mini-map hidden by default.

## Accessibility requirements

- All interactive controls must be keyboard reachable.
- Collapse buttons must expose expanded or collapsed state using `aria-expanded`.
- Floating TOC must use appropriate dialog, popover, or menu semantics.
- Icon-only buttons must have accessible labels.
- Focus should move logically when the TOC opens and closes.
- The current section should not rely on color alone.
- The feature must respect reduced motion settings.

## Performance requirements

- The mini-map must not render the full markdown document a second time.
- Use lightweight structural markers instead of a full visual duplicate.
- Scroll tracking must be throttled, debounced, or observer-based.
- Large markdown files should remain responsive.
- Avoid layout thrashing during scroll.

# Suggested Implementation Tasks

## Task 1: Extract heading outline

Implement a utility that receives rendered markdown or parsed markdown tokens and returns a heading outline.

### Output

```ts
MarkdownHeading[]
```

### Done When

- Headings are detected correctly.
- Nested heading levels are preserved.
- Repeated headings receive unique IDs.
- Rendered heading elements receive matching IDs.

---

## Task 2: Implement floating table of contents

Create a floating Contents button and overlay.

### Done When

- Button appears only when useful.
- Overlay lists all headings.
- Current section is highlighted.
- Clicking a heading scrolls to it.
- Keyboard navigation works.
- `Esc` closes the overlay.

---

## Task 3: Implement collapsible section behavior

Add expand and collapse controls to rendered headings.

### Done When

- Each heading can collapse its own section.
- Nested content hides correctly.
- Expand all and collapse all work.
- State is retained while the file remains open.
- `aria-expanded` is correct.

---

## Task 4: Implement document mini-map

Create a lightweight right-edge mini-map using the heading outline and document block metadata.

### Done When

- Mini-map appears only for long documents.
- Viewport indicator updates during scroll.
- Clicking a region scrolls to that document position.
- Heading markers show tooltips.
- Mini-map does not block text or harm readability.

---

## Task 5: Add reading-mode integration

Ensure all three navigator features work in rendered reading mode.

### Done When

- The user can read without seeing raw markdown.
- Navigation controls do not require editing mode.
- Split mode still works if the app supports it.
- The features do not break existing markdown preview behavior.

---

## Task 6: Add tests

Add tests for outline extraction, section boundary detection, collapse behavior, and TOC navigation.

### Minimum Test Cases

- Document with no headings.
- Document with one heading.
- Document with repeated headings.
- Document with nested headings.
- Document with code blocks containing markdown-like heading text.
- Document with very long sections.
- Document with tables and task lists.
- Collapsing parent heading hides nested subsections.
- Current section updates while scrolling.

# Non-Goals for Initial Implementation

Do not implement these in the first pass:

- Full graph view.
- Backlinks.
- Plugin system.
- Multi-file vault system.
- AI summarization.
- AI rewriting.
- Markdown linting.
- Real-time collaborative editing.

These are separate features and should not block the Document Navigator.

# UX Notes

## Default behavior

When a casual user opens a markdown file, the app should default to rendered reading mode.

The document navigator should support reading, not dominate it.

## Visual hierarchy

Navigation controls should be visually quieter than the document content.

Suggested priority:

1. Document content.
2. Floating Contents button.
3. Collapse controls.
4. Mini-map.

## Empty states

If the document has no headings:

- Hide the TOC.
- Hide collapse controls.
- Hide mini-map.
- Do not show an error.

If the document has only one heading:

- Hide the TOC unless there are many meaningful sub-blocks.
- Collapse controls may still appear.

## Small-screen behavior

On mobile screens:

- Hide the mini-map.
- Keep the floating Contents button.
- Keep collapsible headings.
- Ensure controls are at least 44px tall or wide where practical.

---

# Definition of Done

This feature is complete when:

- A casual user can open a long `.md` file and navigate it without seeing raw markdown.
- The floating TOC allows quick jumping between sections.
- Headings can be collapsed and expanded.
- The mini-map gives a useful structural overview for long documents.
- Keyboard and screen reader accessibility are handled.
- The feature does not degrade markdown rendering performance.
- The implementation is tested against nested headings, repeated headings, malformed documents, and long AI-generated files.
